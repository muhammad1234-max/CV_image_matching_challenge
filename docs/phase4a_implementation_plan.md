# Implementation plan, resource budget and rejection criteria

Planning estimates assume one engineer familiar with the existing worker. Phase 4A ends with this design.

| Stage | Proposed work and artifact | Gate |
|---|---|---|
| 1. Establish data availability | Laptop first. Inventory the four immutable ZIPs, define a versioned opaque graph schema, fixture database and read-only importer with provenance and frame tests. Trace post-pruner tables through all mapper and localization paths. Record missing features explicitly. | Synthetic identity, reversed edge, random gauge, non-finite rotations, disconnected components, duplicate pairs, neutral-ID permutation without ties, canonical tie cases, all-outlier and reflection fixtures. Verify SO(3), inlier index bounds, byte hashes and cache rejection on changed intrinsics. |
| 2. Deterministic reference | Implement graph connectivity, count-weighted spectral proposal, pass-through and local triangle closure reference. Test a path with few loops and a dense bridge dominated by one endpoint. | Missing geometry cannot cause a split. Endpoint-only archives permit checking topology and join counts; they do not qualify geometry. |
| 3. Proposed rule | Implement the two local frames, non-tree closure, disjoint crossing witnesses and abstention. Log every input mask, vote, cut and reason. | Rigid subgraphs connected by a common frame rotation should survive; deliberately incompatible crossings should split. Coherent geometric alias should illustrate a known miss. |
| 4. One real pilot | After approval, use labeled-data-free Haiper branch with a versioned cache capture and matched mapper-off/control + active test. Lock decisions before admin joins. | Verify cache completeness and pass-through, finite proper predicted poses, frozen membership, mask isolation and predefined Haiper gate. Stop if rotation fields are unusable and authorized recovery fails. |
| 5. Fixed four | Use primary neutral seed for ETs, stairs, Haiper and Theater/Church, independent scoring and registered organizer comparator. | Publish per-dataset effects and failures; keep Haiper once. No extra datasets selected by scores. |
| 6. Ablations | CPU replay for every named ablation; rerun mapping for each distinct effective database and export policy. Add the ETs order sensitivity check. | Attribute gains to the claimed component only if matched geometry and ablation results support it. |
| 7. Broader evaluation | Only after gates, evaluate all frozen development groups with shared matching and separate mapper outputs. Lock final configuration and request protected confirmation release. | Full coverage before a full score; one confirmation evaluation. Publish all failed attempts and runtime, including upstream capture. |

**What can be reused.** SHA-256 of all four ZIPs in reports/ns64_full/completed_archive_index.json matches the index. Only Haiper and Theater/Church ZIPs have verified_edges.json, containing opaque endpoint pairs. Counts in stage receipts are summary statistics. ETs/stairs have predictions/receipts; the audited zips do not supply the rotation arrays, keypoint coordinates, verified inlier indices, camera models and mapper-ready database required for A. Theater/Church checkpoint JSONs are receipts, not numerical matching caches. Organizer caches describe a different frontend. If a separate thick ns64 cache is found, validate source revision, exact YAML/weights/environment, image membership/order and hashes, retrieval and verified pair inventories, coordinate scaling, camera model, ID mapping, rotation convention, descriptor/keypoint indexing and stage ABI. Check hash of each payload against a trusted stage manifest, then compare a sample round trip with the same exporter. Reject copied filenames or manifest-only “matches.” Otherwise budget one capture per dataset, read-only shared parent and independent branch-local databases.

**Measured T4 wall times.** Seconds for matching, incremental mapping and whole worker respectively. ETs 107/174/364; stairs 511/366/1,017; Haiper 479/428/1,087; Theater/Church 684/1,297/2,164. Total measured worker wall about 77.2 min, of which approximately 37.8 min was mapping and 29.7 min matching. GPU peak allocated 5.00–5.60 GiB, reserved up to 8.77 GiB, peak worker RSS 6.04–6.49 GiB. Wall includes CPU stages and is not GPU utilization time. Full organizer measurement was at least 13 h 27 min including a timeout. [Measured pilots](step03c8_remaining_compute_plan.md) · [Organizer](step03b_baseline_results.md)

**Forecasts, not measurements.** CPU graph logic on a laptop: seconds to low minutes per N≤225 sparse graph after rotation extraction; budget one minute per pilot graph as a profiling target, not a guarantee. Database decoding or inlier recovery may dominate. Allocate 1 GiB incremental CPU memory for the graph prototype and measure separately from mapper memory. B’s small head fits on CPU; estimate minutes to an hour per fit once features exist, plus 3–6 engineering days. C runs additional CPU maps; 2× wall versus matched control is the pilot stop condition, not predicted speed. A needs zero additional pairs. One capture plus one uncached variant map across the four is approximately 77 + 38 = 115 worker minutes if mapping cost stays like historical, before setup/export/scoring. Each distinct mapper ablation may add another ~38 min on these inputs; an altered partition could cost more or less. Stages 1–3 approximately 4–7 engineer-days including the capture adapter; actual remote capture belongs to stage 4.

Across the other seven development datasets the project’s image-linear and pair-proportional scenarios give 10.76 and 28.39 T4-session hours for one original pass. Including the four measured runs gives approximately 12.05 or 29.68 hours for a hypothetical complete capture. These are two scenarios, not bounds; a failed large COLMAP solve can exceed either. Forecast additional branch maps separately from measured graph sizes, track counts and stage times, and include cold starts, archive transfer and scoring outside the headline estimates. Full ns64 has not been measured. Laptop for graphs and administrative evaluation; same pinned T4 path for cold matching and comparable end-to-end runs. More GPU memory would only be justified by a measured VRAM failure or a separately authorized larger learned comparator, while increasing GPU size alone may leave CPU mapping time unchanged.

**First proposed coding task.** Implement only an opaque, read-only graph inventory and toy-fixture validator, in a new experimental module. Emit pair count, eligible-rotation fraction, units/conventions, closure checks and cache pins. The first acceptance test is that the existing Haiper ZIP is correctly classified as topology-only. No real reconstruction is needed to pass this milestone.
